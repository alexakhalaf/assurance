# Load test, 2026-11-18 (synthetic fleet, mock collector)

Setup: 1,000 synthetic devices (60% IOS-XE, 40% NX-OS), 1,000 extra routes each, 1% route churn in t2.
3 RQ workers, API on uvicorn with 2 processes, PostgreSQL 16 and Redis on the same 4-vCPU / 16 GB host.
2.17M state rows after two snapshots. Fleet size is not confirmed yet, so throughput is given per worker.

## Collection

| Run | Devices | Result | Wall time | Devices/min | Per device p50 / p95 / max |
|---|---|---|---|---|---|
| t1 | 1000 | 1000 ok | 11 min 4 s | 90 | 1.62 / 2.02 / 2.62 s |
| t2 | 1000 | 1000 ok, 36,586 changes | 12 min 25 s | 80 | 1.79 / 2.32 / 3.50 s |

That is about 30 devices a minute per worker on a shared 4-vCPU host (CPU-bound Genie parsing).
Finalize (diff against the previous snapshot plus intent checks) took about 1.5 min for t2 and held
about 1.2 GB in the worker.

## Findings to fix before production

1. Global search for an IP that is in every device's route table loads every matching row and runs
   the route lookup in Python: the API process grew to 7 GB and was killed. It needs a row cap, a
   SQL-side prefix match (inet/cidr columns or a GiST index), and streaming.
2. Pre/post (`/compare/prepost`) on a 1,000-device diff died the same way; it materializes the full
   diff and both state sets in memory.
3. Snapshot finalize loads all state rows with their data for the diff and checks (about 1.2 GB for
   2.2M rows). It must stream or diff in SQL by row_hash.
4. The p95 tail on dashboard, routes diff and the change report (16 to 42 s) comes from the process
   above being starved or killed while those requests waited; rerun after fixes 1 to 3.
5. Text search is a sequential `ilike` over the JSON cast of every row (4 to 12 s). Needs a
   trigram index or a search column.
